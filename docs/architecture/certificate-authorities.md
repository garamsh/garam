# Certificate Authorities

The certificate authority an organization signs machine identities
with (ADR-0014). Implemented by `internal/ca`, whose PostgreSQL store
is `internal/ca/postgres`.

| Type | Responsibility |
|------|----------------|
| `Authority` | an organization's CA: the certificate it signs with, and its private key in sealed form |
| `Certificate` | a signed client certificate, the CA that signed it, and the serial that tells it from another certificate naming the same subject; it holds no key, because the key may be one garam never saw |
| `IssuedCertificate` | a `Certificate` garam generated the key pair for, carrying the private key it returns once |
| `Sealer` | seals key material so what reaches storage is useless without the key-encryption key the process holds |
| `Service` | issues a certificate for a subject GRN over a key it generates, or signs one a certificate request carries, creating the organization's CA on demand |

`Authority`'s fields are exported and it has no accessors: every one
of them is a value the store writes and reads back, and the aggregate
holds no invariant over any of them
([ADR-0069](./adr/0069-the-aggregates-are-data-carriers-so-the-driver-leaves-the-domain-package.md),
superseding ADR-0051's accessor for this aggregate). `Certificate` and
`IssuedCertificate` keep theirs: no store here writes either, so
neither is a value that decision reaches.

A CA is an organization's own rather than shared, so a certificate
issued by one does not chain against another's and tenancy holds in the
trust root rather than in a check a caller could forget. It is created
on the first certificate that organization needs, so an organization
that has needed none has no authority yet. The subject's GRN travels in a
SAN URI and the certificate carries nothing else — no name, no roles, no
claims. Lifetime is what bounds an agent's certificate and nothing
withdraws one (ADR-0014), so it is short by default and bounded at both
ends — a service whose configured lifetime falls outside them does not
start — and it carries jitter that only shortens it, which keeps a
fleet from expiring together (ADR-0015). An operator's certificate is
bounded at the other end as well: it stops authenticating when the
organization deletes the operator, which is decided against the record
rather than against anything this domain signs or holds (ADR-0070).
A lifetime reaching past what the signing CA has left is refused rather
than signed: such a certificate stops verifying the day the CA expires.

The CA private key reaches Postgres only through `Sealer`, whose one
implementation is AES-256-GCM under a key-encryption key read from a
file through `internal/keyfile` (ADR-0015); the sealed bytes name the
key that opens
them, and open only in the organization's row they were written for, so
write access to the database moves no trust root. A subject's own key
reaches a certificate one of two ways: generated per certificate and
returned once, never stored, or generated by the subject in its own
cluster and sent as a certificate signing request garam signs without
ever holding it (ADR-0064).

`garam serve
machine` is the process that issues, and it reads the key-encryption
key before it serves: the process that owns the authorities refuses to
start without the key that opens them rather than failing at the first
certificate it is asked for. `garam issue-certificate` reads the same
key the same way and mints an operator's own first certificate out of
band. It refuses any subject that is not an operator, and no serve path
reaches it, which is why the command is a sibling of `serve` rather
than a subcommand under it. That is as far as the refusal and the
command tree reach: `garam serve machine` mints identities and issues
certificates on the listener it serves, an operator's first among them
— once per enrollment token, for the one operator that token names
(ADR-0064).

That key is as availability-critical as the database — losing it loses
every organization's CA with no recovery short of new authorities and a
reissue for every certificate — and why it is held this way rather than
in a KMS is [ADR-0016](./adr/0016-ca-key-custody.md).

**An authority is lost the same way when its organization is deleted,
and nothing here brings one back.** The row is keyed on the
organization and goes with it, sealed key included
(`migrations/000005`). `Store` declares `Create` and `Get` and no
more: there is no import, no restore, and no route that re-creates an
authority for an organization that is gone — and `Create` would need
an organization row the same delete removed. What the service creates
on demand is a *new* authority for an organization that exists, which
verifies nothing the old one signed. So every certificate that
authority issued stops authenticating permanently, an operator's
included: `operator_certificates` keeps its row (ADR-0045 errata) and
that row's certificate no longer chains to anything.

The browser API states this before the act rather than after it.
`getOrgDeletionPreview` reports whether the organization holds an
authority, as its own field and not as one entry among counts, because
it is the only thing a deletion takes that cannot be made again;
[organizations.md](./organizations.md) holds the rest of what that
deletion reaches. The listener reads presence alone, through a seam
the composition root satisfies, so it holds no key and opens nothing
([domains.md](./domains.md)).
